# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Én Pust Til** — a free-diving arcade game for the Capra booth at JavaZone 2026 (2–3 September, NOVA Spektrum). Kotlin 2.2.20 on [Pulse Engine](https://github.com/NiklasJohansen/PulseEngine) 0.13.0, shipped as a Windows `.exe` with a bundled JRE.

The design is **locked**: `docs/superpowers/specs/2026-08-04-en-pust-til-design.md` is the single source of truth for game rules, economy, controls and presentation. Read the relevant section before changing behaviour; §17 has the amendment log and the platform findings that constrain implementation. `docs/superpowers/plans/2026-08-04-en-pust-til-gameloop.md` is the implementation plan, and `.superpowers/sdd/2026-08-04-en-pust-til-gameloop/` holds the per-task reports with the empirical evidence behind many of the odd-looking decisions in the code.

**TARGET CORRECTED 2026-08-30: this build runs on a standard Mac with a controller attached, NOT on an arcade cabinet.** The owner said so directly. Everything below that reasons from a cabinet still describes real, working, tested machinery and is left in place — the booth hardening (`booth/`, the unattended-recovery timeouts, the unmapped-encoder diagnostics) is not wrong, it is simply no longer the thing driving decisions. Read the original framing that follows as history, and weight it accordingly before optimising for a queue that will not exist: a controller that works fully and correctly is now the priority, which is exactly why the `MappedPads` entry in the platform-constraints list below matters more than anything about encoders.

The original framing: the target was a **two-day unattended arcade cabinet in front of a queue**. That drives most of the non-obvious engineering: the cabinet must recover to attract mode on its own, must never lose scores, and must not depend on a keyboard or a console being attached.

### Seeing it actually run

Tests passing is not evidence the game looks right — a lot of the bugs in this project's history were invisible-in-tests rendering faults.

**The title on screen is English and every identifier is not, so `pgrep -f EnPustTilKt` below is still correct.** `ScreenText.TITLE` has read `"ONE MORE BREATH"` since 2026-08-30; the main class is still `EnPustTilKt`, `GAME_NAME` and `application.cfg`'s `gameName` are still `EnPustTil`, and the rename was deliberately kept player-facing so every capture and recovery procedure in this file keeps working verbatim. Do not "finish" it in the days before a booth — and if you ever do, `GAME_NAME` and `gameName` must move in lockstep, because `configFileHealthWarning` compares them at startup and would otherwise log a config-corruption warning at every boot with nothing wrong.

**GRAB THE REAL WINDOW. `EPT_SCREENSHOT` IS NOT PASSIVE AND ITS OUTPUT IS NOT THE FRAME.** Both halves of that cost a full day of wrong conclusions on the cliff work, where a dozen "before/after" measurements were quoted as evidence and none of them matched what was on the owner's screen:

- `ScreenshotEffect.getTexture()` returns `RenderTexture.BLANK`, so **any surface it is attached to composites as blank**. With `EPT_SCREENSHOT` set, the sky surface came out black in the running game. The tool changes the frame it claims to be observing.
- It dumps each surface SEPARATELY (`-0` world, `-hud`, `-sky`). Recompositing those by hand does not reproduce the engine's frame — the rock came out a pure black silhouette in the dumps and lit, textured stone on screen. Any brightness, contrast or texture-variance number taken off a recomposite is worthless.

So use it only to inspect ONE surface's raw contents (its alpha channel is genuinely useful — that is how the quad-edge slivers were found), and take anything about *appearance* from a real screen grab:

```bash
caffeinate -d -u -t 900 &                      # macOS: stop the display sleeping mid-capture
./gradlew run > /dev/null 2>&1 &
until pgrep -f EnPustTilKt > /dev/null; do sleep 2; done ; sleep 8
osascript -e 'tell application "System Events" to set frontmost of (first application process whose name is "java") to true'
sleep 2 ; screencapture -x -o /tmp/shot.png    # needs Screen Recording granted to the terminal
pkill -9 -f EnPustTilKt                        # the game has no quit key in booth mode
```

The JVM window has **no bundle identifier**, so the computer-use MCP filters it out of its screenshots entirely — the shell route above is the one that works.

**`osascript`'s `System Events` `keystroke`/`key code` is silently dropped by this window** — confirmed by a control test where the identical command was delivered to TextEdit, so the loss is the GLFW/LWJGL window under `-XstartOnFirstThread`, not the automation. This matters because the game boots into IDLE and reaching the water needs a keypress. What works is posting one level lower, `Quartz.CGEventPost(Quartz.kCGHIDEventTap, ...)` from Python.

So the block above only ever photographs the **attract screen**. Anything in the water needs the press, and this is the exact sequence that produced the sandbank's verification frames — copy it rather than re-deriving it, because every `osascript` route through it is a dead end:

```bash
caffeinate -d -u -t 900 &
EPT_DEV=1 EPT_DEPTH=160 ./gradlew run > /tmp/run.log 2>&1 &
until pgrep -f EnPustTilKt > /dev/null; do sleep 2; done
sleep 8                                    # let DiverSprite's asynchronous sheet upload finish (SpriteSheet.textures
                                            # populates in onUploaded, several frames after asset.load queues it, and
                                            # sheetsReady() gates the diver's draw with a placeholder rectangle until
                                            # then) — verified at this value: a screencapture taken at exactly this
                                            # timing on 2026-08-30 shows the baked diver sprite, not the placeholder
osascript -e 'tell application "System Events" to set frontmost of (first application process whose name is "java") to true'
sleep 0.5
python3 - <<'PY'                           # System Events will NOT deliver this keypress
import Quartz, time
def post_key(keycode, down):
    Quartz.CGEventPost(Quartz.kCGHIDEventTap,
                       Quartz.CGEventCreateKeyboardEvent(None, keycode, down))
SPACE = 49
post_key(SPACE, True); time.sleep(0.05); post_key(SPACE, False)
PY
sleep 6                                    # ride out the briefing's five-second dwell
osascript -e 'tell application "System Events" to set frontmost of (first application process whose name is "java") to true'
sleep 0.5 ; screencapture -x -o /tmp/shot.png
pkill -9 -f EnPustTilKt ; pkill -f caffeinate
```

The second `frontmost` call is not redundant — focus can be lost across the briefing dwell, and a capture taken without it photographs whatever took the focus instead. `EPT_DEPTH`'s pin survives the transition, because `applyDepthPin()` re-fires inside the `lifecycle.justStarted` branch, immediately before `camera.snapTo` — an order `EnPustTilDepthPinTest` asserts — so the diver really is at the pinned depth for the first seconds of the run, not just in attract mode. The six-second wait is `RunLifecycle.BRIEFING_SECONDS` (5 s) plus a margin.

**Pinning `EPT_DEPTH` at `Tuning.MAX_DEPTH` burns air almost instantly** — a run can auto-surface within roughly 14 s of wall-clock, so a capture aimed at that depth has to run promptly after the pin takes rather than after the usual settle time.

**Validate that a `screencapture` actually contains the game before drawing conclusions from it.** A capture that returns the macOS lock screen looks exactly like a successful one unless something checks it — this is not hypothetical, a full capture cycle was lost to exactly that on this project.

`render/ScreenshotEffect.kt` is a debug tool, not a feature: it captures at frame 180 by default, and it derives its filename via `outputPath.replace(".png", "-$index.png")` — so if `EPT_SCREENSHOT` has no `.png` in it, the file is written with no extension at all.

`EPT_DEV=1` forces `logLevel = DEBUG` (works even against a built release `.exe`), draws the gamepad diagnostic overlay, and adds the `MetricViewer` overlay — **NOT bound to F3, despite the name**: `engine.service.add(MetricViewer())` alone never called `.start()`, and `Service.isRunning` defaults false with `ServiceManagerImpl` skipping every non-running service, so the overlay was registered and never once ticked, for the whole life of this project, verified from bytecode and by driving F3 into the running game and screenshotting a blank result. Task 1 of the rendering-performance plan added `.also { it.start() }`, which makes it tick — but `MetricViewer`'s only `isRunning` toggle is the console command `showMetricViewer`, registered in its own `onCreate`, and that console is unreachable in this project (no `CommandLine` widget is ever constructed — same root cause as the dead F1 console). So the overlay is now **permanently visible whenever `EPT_DEV=1`**, with no way to turn it back off, not gated by F3 at all. It graphs `engine.data.getMetrics()`, which `DataImpl.init()` seeds with eight metrics before `ServiceManagerImpl` adds its own three service timers (`javap -p -c -constants` on `DataImpl.class`, `addMetric` calls at bytecode offsets 51-143): FRAMES PER SECOND (FPS), FRAME TIME (MS), GPU RENDER TIME (MS) — this is the CPU-around-`drawFrame` number, not a real GPU timer, see `FrameProbe`'s class doc — CPU RENDER TIME (MS), CPU UPDATE TIME (MS), CPU FIXED UPDATE TIME (MS), USED MEMORY (KB) and MEMORY OF TOTAL (%). So it DOES show fps and frame time, contrary to an earlier version of this line. It is still not the instrument to measure with: it is a visual overlay with an always-on draw cost of its own under `EPT_DEV=1`, so **never measure frame time with `EPT_DEV=1` set** — use `EPT_PROFILE=1` (`render/FrameProbe.kt`) alone, which is what the baseline in `FrameProbe`'s class doc was taken with. It prints `[FRAME] p50=... p95=... worst=... n=...` once a second to stdout and has no per-frame draw cost of its own.

`EPT_FAIL_BOOT=1` makes `createGame` throw deliberately, right after the `"hud"` surface is created but before `sim`/`scoreRepository` are constructed — the one `createGame` failure `EnPustTil.worldUnusable` treats as unrecoverable. It exists so the booth's full-frame `!! BOOT FAILED - RESTART THE CABINET !!` screen (`render.BoothStatus`, `EnPustTil.drawBootFailedScreen`) can be rehearsed and photographed before a booth, rather than trusted on reasoning alone. Unset at the booth: one getenv at startup, same cost as every other `EPT_*` flag here.

`EPT_BRIEFING_HOLD=1` pins the pre-run briefing open indefinitely — it then leaves only on a
press. The documented attract-screen window-grab route (the first recipe above) takes about ten
seconds to reach a `screencapture` (`sleep 8` for the asset upload to settle, then `sleep 2`
before the capture) — longer than the briefing's five-second countdown, so without this
the one screen that most needs a real frame is the one screen that cannot be captured. It
passes `Float.POSITIVE_INFINITY` as `briefingSeconds`, and `drawBriefingScreen` suppresses the
countdown line on `briefingAutoStarts` — `Float.POSITIVE_INFINITY.toInt()` is `Int.MAX_VALUE`,
so the pinned screen would otherwise read `STARTING IN 2147483647`. Unset at the booth.

**F1 DOES NOT OPEN A CONSOLE, and `winner` therefore cannot be typed.** This line used to claim it did, and the claim is repeated at `score/ScoreRepository.kt:155` and in `score-persistence-report.md:26`. `ScoreRepository.registerWinnerCommand` registers the command correctly and ungated (not behind `EPT_DEV`), but nothing ever constructs the widget that reads input: in `pulse-engine-0.13.0.jar` the string `showConsole` occurs only inside `no/njoh/pulseengine/modules/cli/CommandLine.class`, no class in the jar or in this project references `cli/CommandLine`, and `src/main/resources/init.pes` separately records that the engine never runs a `.pes` script at all — so the `bind F1 showConsole` line in that file is inert. `CommandLine` extends `Service`, so `engine.service.add(CommandLine())` in `onCreate` is the plausible one-line fix; it is UNTESTED. If the end-of-day raffle matters, test it before the booth rather than discovering this at the stand.

## Architecture

Four packages plus `EnPustTil.kt` at the source root, and the boundaries between them are the important part.

**`dive/` — the simulation.** Pure Kotlin, zero engine imports, ticked at a fixed 60 Hz. `DiveSim` holds all run state and its `tick(dt, DiveInput)` is the whole game. `Tuning` holds every tunable constant and no logic. `Zone` is the depth bands (value, mass, air burn). `Buoyancy` is the movement model — an empty diver is *neutrally buoyant and hovers*; carried mass is what makes you sink and what makes you sluggish, which is the design's central mechanic (§4), not a rendering detail.

**`render/` — the engine shell.** `EnPustTil.kt` is the only `PulseEngineGame`: it reads input, gates the sim on lifecycle state, and draws. `RunLifecycle` is the MAIN_MENU → BRIEFING → PLAYING → RUN_OVER → ENTER_INITIALS state machine (plus IDLE and PAUSED) — pure and engine-free, so the booth's whole unattended-recovery behaviour is unit-tested. **`RunLifecycleState.MAIN_MENU` is the boot state (2026-08-31), not IDLE.** IDLE is now the idle *fallback* an abandoned menu falls back to on `MENU_IDLE_TIMEOUT_SECONDS`, and any press from IDLE returns to MAIN_MENU rather than straight into a run — attract is a second way to REACH the menu, not a second way to start a dive. **BRIEFING is entered only from MAIN_MENU (`menuAction`, i.e. confirming START DIVE) — a retry from RUN_OVER goes straight back to the water, and IDLE no longer opens BRIEFING directly at all: a fresh press from IDLE now lands on MAIN_MENU, not on a new run.** **PAUSED now has two halves that share nothing but the state (2026-08-31).** From IDLE it is the technician's cabinet menu: `drawPauseScreen`, closed by a second pause edge, exit by hold — unchanged. From PLAYING it is the MAIN MENU itself, drawn over the frozen dive with its first row relabelled CONTINUE (`RunLifecycle.runHeld`, `ScreenText.MENU_CONTINUE`), so Esc mid-run reaches GRAPHICS, LEADERBOARD and QUIT rather than a second screen that would have had to grow its own copies of all three. **A pause edge deliberately no longer resumes a held run** — `pauseButtonAlt` and `restartButton` are the SAME button by shipped default (Options), so one press raised the menu's confirm and a pause edge together, and resuming on that edge meant picking GRAPHICS dropped the player back in the water. A held run leaves through `RunLifecycle.resumeRun()`, which `EnPustTil.applyMenuAction` calls for CONTINUE (`MenuAction.StartDive`) and for back-on-the-root-page (`MenuAction.CloseMenu`, new — root-page back used to return `None`); on GRAPHICS the same press is `MenuAction.Back` and stays with the menu, which is what keeps Esc from surfacing a player mid-page. `PAUSE_IDLE_TIMEOUT_SECONDS` now resets on `menuInputActive` for the same reason `MENU_IDLE_TIMEOUT_SECONDS` does — the screen has a GRAPHICS page a player can spend a while on. Picking LEADERBOARD from a held run ABANDONS it (`viewLeaderboard` -> IDLE -> `justReturnedToIdle` -> fresh `DiveSim`); that is the only "leave the dive" route, and it beat leaving the row inert on a screen a player navigates blind. `PauseMenuWiringTest` is the source scan over the `EnPustTil` half, which needs a GL context and so cannot be reached from a unit test. `DiveRenderer` draws the world to `mainSurface`, `DiveLighting` issues immediate-mode `drawLight` calls, `Hud` draws to a separate `"hud"` surface, `DiveCamera` eases toward the diver, and `DiverSprite` owns the diver's art — the two baked sprite sheets, the animation loop and the body's size and rotation. `SandBank` owns the seabed at the foot of the trench: one quad exactly `Framing.VISIBLE_WIDTH_METRES` across at `uTiling = vTiling = 1`, drawn in `DiveRenderer.render`'s fixed order — zone bands → backdrop → sea quad → **sandbank** → walls → air pockets → pearls → anglerfish → diver → motes — so the cliffs' ragged silhouette sits over its ends rather than the other way round.

**`render/Look.kt` is the presentation twin of `dive/Tuning.kt`: every number that decides how the game LOOKS, values only, no logic.** Sky gradient, sun colour, the water's own colour ramp, the daylight tables and their floor, the torch, the pearls, the motes, and the colour grade — each one declared here and referenced from the file that uses it, so the owner has one page to tune from. The *reasoning* deliberately stays at the consumer (`DiveLighting`, `DiveRenderer`, `Sky`, `Motes`), because that is where someone about to change behaviour will meet it; `Look` carries a one-line summary and a `@see`. Correctness constraints are deliberately NOT here — `GI_REFLECTANCE_FLOOR`, `Motes.FIELD_TOP_DEPTH`, `OpaqueWater.GATE_DEPTH` and `MoteSprite.ALPHA_RAMP_OUTER` are solved against the engine, not chosen, and a page headed "tweak to taste" is the wrong home for them. **If the build fails after an edit there, the test message is a design rule speaking** — the >10x Shallows-to-Abyss water ratio (§11), the ambient floor's blue dominance, the mote-versus-pearl hue separation (outstanding-work §1.1), and the GI reflectance floor are all asserted relationships rather than values.

**Eighteen PNGs ship, and three more textures are generated in code.** The files: `DiverSprite`'s two sheets (`sprites/diver-{diffuse,normal}.png`), `RockFace`'s ten (`backdrop/rock-*.png` — wall, crest, body and the baked mirrors of each, diffuse and normal), `Backdrop`'s three parallax silhouettes, `SandBank`'s two (`backdrop/sandbank-{diffuse,normal}.png`, 2000×500 — the seabed at the foot of the trench; the three paragraphs below cover its derivation and its two traps), and `sprites/oxygen-normal.png`. (This paragraph read "Sixteen … and three" for as long as the sandbank did not exist.) That last one is `OxygenSprite`'s: a 96-frame normal-map-only sheet (11×9 cells of 182×216, 2002×1944) with no matching diffuse, because a vent's colour comes from `setDrawColor` at the draw site — live versus spent is that colour and nothing else — and its optics come from `shaders/iridescence.frag`. **It is wired**: `EnPustTil.onCreate` queues it beside the diver's, `onFixedUpdate` advances its loop inside the same `lifecycle.spriteAnimates` gate, and `DiveRenderer.drawAirPockets` draws each vent through the iridescence shader with that frame's cell as `normalTex` and then submits the same rect to `gi_normal_map`. (This paragraph read "**baked but NOT YET WIRED** — no Kotlin references it" for as long as that was true; it is committed regardless of wiring because `assets/oxygen_sprites/` is gitignored and the sheet would otherwise be unrecoverable.) The generated ones are `render/LightEmitter.kt`, `render/PearlNormalMap.kt` and `render/MoteSprite.kt`. Everything else — the pearls, the HUD, the water and zone bands — is still `Texture.BLANK` through `Draw.kt`. (This paragraph read "the diver is the only asset with a FILE behind it… two that are generated" long after the rock art and `MoteSprite` landed.) All three generated textures are built in code at load (`loadFrom` + `engine.asset.load`, filled *before* they are queued) rather than shipped as PNGs, and `PearlNormalMap`'s case is the stronger one: `shaders/iridescence.frag` already computes the pearl's hemisphere normal and physically cannot share it (a `BatchRenderer` draws to one surface; GI reads normals from `gi_normal_map` through a *texture*), so the second copy is generated from the same formula and `PearlNormalMapTest` asserts the two agree against the shader source on disk.

**The sandbank's bake carries its own metadata dict and its own fingerprint, and must not join the shared one.** `tools/build_backdrop.py` builds ONE `meta` dict for the rock and silhouette outputs, whose `ept:source_sha256` hashes `sorted(ROCK_DIR.glob("*.png")) + sorted(SILHOUETTE_DIR.glob("*.png"))`, and hands that same dict to all thirteen of its existing `write_png` calls (4 wall + 4 crest + 2 body + 3 silhouette) — sharing it is correct THERE because the rock body is a crop of the wall's own already-lifted output and legitimately carries the wall's provenance, not independent art. The sandbank is independent art from a separate source directory nothing else derives from, so it gets a `sand_meta` dict of its own, fingerprinted over `assets/sandbank/*.png` alone. Joining the shared dict would change `ept:source_sha256`, which changes the metadata on all thirteen OTHER committed PNGs for a metadata-only edit, spending the exact "an unchanged re-bake produces no git diff" guarantee the shared dict exists to protect. **The operational consequence: a sandbank re-bake must show exactly TWO changed files. If it shows fifteen, the fingerprint has reached the shared glob, and that is a bug to fix, not to commit.**

**`SandBank`'s geometry runs FROM THE ART OUTWARD and must not be re-inverted.** `SandBank.QUAD_TOP_DEPTH` (160.30069 m) is the one placement a human chose; the crest depth is measured DOWN FROM it, through the sheet: `MEAN_CREST_DEPTH = QUAD_TOP_DEPTH + CREST_OFFSET_METRES`. Written the other way round — `MEAN_CREST_DEPTH = Tuning.MAX_DEPTH + DiverSprite.FIN_REACH_METRES` — `SandBankTest.the sandbank's mean crest and the diver's fins put him on the floor at MAX_DEPTH` substitutes to `(a + b) − b == a`, an identity no edit anywhere can falsify. Both forms produce identical numbers, so the direction is invisible except in the expression, which is exactly why it needs writing down. `Tuning.MAX_DEPTH` stays the literal `160f`, because `dive/` may not import `render/` — so what actually enforces "derive it from the art" is a three-part ring of tests, not an expression: `DiverSpriteTest.the fin reach is the deepest opaque row of any frame, re-derived from the committed sheet` re-derives `FIN_REACH_METRES` from the diver's own art, `SandBankTest.the mean crest row is re-derived from the committed diffuse's alpha` re-derives `MEAN_CREST_TEXEL_ROW` from the sand's, and the relationship test above ties both to `Tuning.MAX_DEPTH`. `Framing.SEA_FLOOR_DEPTH` (184.9296 m, the camera's floor clamp) is a separate literal rather than a read of `SandBank.QUAD_BOTTOM_DEPTH`, on purpose: `DiveCamera` is pure Kotlin with no engine imports, and `SandBank` is an object full of engine `Texture` descriptors — the read would only work today because `QUAD_BOTTOM_DEPTH` is a `const val` the compiler folds in, and demoting it to `val` would have `DiveCameraTest` constructing textures in a headless JVM. `SandBankTest.the camera's sea floor and the art's quad bottom are the same depth` is what keeps the two literals from drifting apart.

**A normal map baked in the wrong axis — the sandbank's, and it took a swizzle to notice.** `assets/sandbank/normal.png` was authored WORLD-SPACE Y-UP — what exporting a seabed rendered top-down gives, where a floor's own surface normal points along world +Y — while every other normal map in this project is Z-dominant: decoded mean vector (each texel normalised before averaging, over alpha > 16) `(−0.008, +0.900, +0.381)` against `assets/rock/normal.png`'s `(+0.161, +0.058, +0.755)`. Shipped unswizzled, the seabed lights like a WALL, which reads as a lighting bug somewhere else entirely — **and this defect is invisible in every test and in every still frame**, because a still frame does not show light *moving* the wrong way across the dunes as the torch sweeps. `tools/build_backdrop.py`'s `swizzle_yz` does the y↔z swap (`vectors[..., [0, 2, 1]]`), and the sign is NOT flipped: `+y = up/shallower` is settled in this repo by `shaders/iridescence.frag:258` and `render/PearlNormalMap.kt:174-214`'s two-build capture probe, not re-derived here. Post-swizzle the sandbank's mean vector is `(−0.008, +0.381, +0.900)` — Z-dominant, with the same small upward tilt `rock-top-normal.png` already carries at its crest, which is correct for a floor billboard catching light from above. `SandBankTest.the committed normals are unit length, Z-dominant and face up` is what separates a dropped swizzle, a flipped sign, and a dropped sRGB decode, because each of the three fails silently in its own way and none of them fails a still frame either.

**The bake's gain trap: the sandbank does NOT inherit the rock wall's reflectance lift, and it did at first.** `bake_rock_top` and `crop_body` both take the wall's solved gain so a join between two lit surfaces drawn edge to edge does not step in brightness — sound reasoning for art cropped from or sharing statistics with the wall, and it was applied to the sandbank on the same reasoning. It is wrong there: the wall's gain (~3.639) was solved against a dark cliff source, and the sand source is not dark (linear length min 0.5484, median 0.6904, max 0.8413 over its opaque texels) — applying that gain saturated the first baked sheet to **99.999% pure white**, destroying every dune and every shading gradient, and the reflectance GATE did not catch it because saturated white trivially clears a floor. Measured directly: the UNLIFTED sand's darkest texel sits at **27.4× `GI_REFLECTANCE_FLOOR`** (0.02), so the lift was never rescuing anything here — a texel that starts 27× above the floor has nothing to be rescued from. The reflectance gate itself still runs (`tools/build_backdrop.py`'s `bake_sandbank` raises if any baked texel falls under the floor); only the LIFT was removed.

**A light's emitter quad is a region that rasterises into the scene, and its shape comes from the texture's ALPHA.** `GiSceneRenderer.drawLight` with `Texture.BLANK` means "no texture", so the whole quad emits — corners included — which is what put a square halo around every pearl and a hard-edged rectangle around the diver. Two separate defects came out of that and both are now fixed in `DiveLighting`: the *shape*, by generating a radial-alpha disc at load (`LightEmitter`), and the *size*, by decoupling `DIVER_LIGHT_SIZE_METRES` from the diver's height and shrinking it — to a 1.2 m torch head, and to **0.45 m** on 2026-08-21 when the owner asked to be rid of the disc entirely (*"I only want the actual lightbeam"*). The size was the bigger of the two — at body scale no shape helps, you simply see the emitter instead of the light — and it is the ONLY lever that hides the source: `GlobalIlluminationSystem.sourceIntensity`, the uniform that literally scales a light's own body, was captured at 0 and replaces the bright disc with a black one (`Look.TORCH_SIZE_METRES` has both captures). **Shrinking the emitter also raises its radiance**, because `intensityFor` divides by the size to hold the delivered irradiance — which is why `TORCH_FORWARD_FRACTION` had to move the torch OFF the diver's face at the same time, inverting a bound that had held since the emitter was three times wider. The falloff must live in alpha and NOT in colour: GI samples a light's colour where a ray *hits* it, i.e. on its rim, so a colour ramp that reaches zero at the rim scales all escaping light to zero. **`radius = 0` on every call used to mean there was no distance falloff at all** — a light's reach was then linear in its quad's size, which is why shrinking the emitter had to be paid for in intensity. **That stopped being true on 2026-08-13** (`5dc5f7a`): every call now passes `radius = DiveLighting.falloffRadius(reachMetres, pixelsPerMetre)` and irradiance falls as `1/d²`. This sentence is left standing, corrected, because the stale version *actively misled an expert reviewer* into attributing flat-looking lighting to an absent falloff — the real cause is below.

**A pearl used to look the same at every depth, and there were THREE causes, not one.** The first two are fixed; the third is structural and is the one to read before re-opening this. Measured on pinned window grabs at 20/75/140 m (`EPT_DEPTH` + all three phase pins; a same-build control pair agrees to 0.01/255, so any difference below is real), pearl-body median luminance against the open water beside it:

| | 20 m | 75 m | 140 m | water at 140 m |
|---|---|---|---|---|
| before | 113.6 | 83.0 | 88.4 | 0.29 |
| after | 83.5 | 43.8 | 48.0 | 0.29 |

1. **`R` is the radius of FULL brightness — inside it there is no falloff at all.** `PEARL_REACH_METRES` was 3 m against a pearl whose drawn radius is 0.677 m, so the whole pearl sat inside its own `clamp(…, 0, 1)` ceiling. The distance term was present, correctly converted and switched on at a distance nothing in the picture ever reached. It is now **0.25 m — the emitter's own radius** — so the pearl's light falls off from its own surface outward and is at 14% by its silhouette.
2. **A GI light cannot avoid illuminating its own body**, so the only lever is the emitter's size *relative to the silhouette*. At 1.2 m against a 1.354 m disc the emitter covered **79% of the pearl's area**; it is now **0.5 m, i.e. 13.6%**, and the other 86% is lit by the world. It cannot go much below that: the emitter is rasterised into the half-scale local scene and `scene.vert:86-88` floors a light quad at 0.142 m on a 1080p booth panel.
3. **Below the Kelp, NOTHING in the irradiance ramps with depth** — and this is why a pearl still measures the same at 75 m as at 140 m. `DiveLighting.updateAmbient` hands GI one ambient colour floored at `(0.16, 0.30, 0.44)` (`AMBIENT_FLOOR_*`, which exists so the diver is not algebraically black at 140 m), and `final.frag:49` adds it unconditionally, after the normal-weighted gather. The *water* darkens with depth only because `DiveRenderer.drawZoneBands` puts the ramp in the water's own **albedo**; a pearl's albedo carries no depth term. So a pearl responds to the world between the Shallows and the Twilight and has no world left to respond to below it. **Do not fix this by making pearl emission depth-dependent** — spec §17 removed that rule deliberately (*"I'd rather like the diver to have to find them using their flashlight"*). The same flat floor is why the rock measures 1.9–2.0 at every depth below 40 m.

**A pearl is lit as a flat quad unless something submits a normal map, and for a long time nothing did.** `gi_normal_map` had only the diver and the rock on it, so a pearl had no lit side and no dark side: measured over the outer 40% of each pearl's radius, the torch-facing half against the far half was **−0.3% at 140 m**. `render/PearlNormalMap.kt` generates the hemisphere `iridescence.frag` already draws with and `DiveRenderer.drawPearlSurface` submits it on the *same world rect* (a copied argument list — see `drawDiver`); that is now **+10.7%**. The ceiling on it is cause 3 above: the flat ambient floor is most of the light a pearl receives at 140 m and is not normal-weighted. Bloom was ruled out as a cause by capture — `intensity = 0` measures +11.0% against +10.6%, and the pearls sit under the 1.4 threshold entirely.
 `DiverSprite` declares both sheets, `EnPustTil.onCreate` queues them with `engine.asset.load`, and the upload is ASYNCHRONOUS — `SpriteSheet.textures` is populated in `onUploaded`, several frames later, and `getTexture` before that throws rather than returning null. `DiverSprite.sheetsReady()` is the gate, and it doubles as the crash guard: it tests `size >= FRAME_COUNT`, which is 0 before the upload AND 0 if the constructor's argument order was got wrong, so both degrade to a placeholder rectangle plus one WARN instead of an exception in front of a queue.

**One heading, two renderers.** The diver's body is drawn rotated to `DiveLighting.beamHeadingDegrees` — the torch's smoothed aim — so he faces where his light points. That heading is integrated ONCE, in `DiveLighting.updateAim` on the fixed tick, because `DiveRenderer` runs before `DiveLighting` inside `onRender` and a body reading it there would be a frame behind the beam. The two angle conventions are not the same number: `GiSceneRenderer` measures counter-clockwise from +x with +y UP, the sprite's rest orientation is head-up, and the offset between them (`DiverSprite.bodyAngleFor`) was derived from `texture.vert`'s own rotation matrix and then confirmed by capture.

|---|---|---|

| `"sky"` (`Sky.SURFACE_NAME`, created at `EnPustTil.kt:812`) | `engine.gfx.mainCamera` — the same object | **world metres**, same as `main` |
| `"hud"` | its own identity `DefaultCamera` (created by passing `camera = null`) | **screen pixels** |

There are **three** surfaces of ours, not two — this table listed only `main` and `"hud"` for a
while, which invites the conclusion that the sky is on one of them. It is neither, and `Sky`'s class
doc spends two sections on why. `"sky"` sits at `mainSurface.zOrder + Sky.Z_ORDER_OFFSET`, i.e.
*behind* `main`, and is deliberately BLANK below the waterline so an opaque world has nothing wasted

`render/CameraRig.kt` is the **only** writer of `engine.gfx.mainCamera` — `MainCameraOwnershipTest` enforces that by source scan, because a second writer is precisely the bug `6ea1f53` fixed. `render/Framing.kt` (which used to be `Viewport`) holds the framing constants and **owns no transform at all**: there is no `screenX`/`screenY`/`depthAt` any more, and `ViewportTest` was dissolved rather than ported — see `FramingTest`'s class doc for which of its nine cases survived and why the other six did not. `DiveRenderer` and `DiveLighting` therefore contain no coordinate maths; they hand the engine metres and ask the camera (`isInView`, `topLeftWorldPosition`) what is on screen. `Hud` is handed a screen position and a pixels-per-metre scale and stays pure screen space.

**The invariant worth remembering, and it has TWO regimes now.** `CameraRig.pixelsPerMetre` is `max(H / VISIBLE_DEPTH_METRES, W / VISIBLE_WIDTH_METRES)` — the LARGER of a height fit and a width fit. The design aspect where they are equal is **1.6419**, which is *below* 16:9 (1.778), so a 16:9 panel is in the second regime:

- **At or below 1.6419** the height binds: exactly `Framing.VISIBLE_DEPTH_METRES` of water is visible vertically, and a wider display shows more water sideways.
- **Above 1.6419** the width binds: exactly `Framing.VISIBLE_WIDTH_METRES` (98.516 m) is visible across, and the visible DEPTH falls off as `98.516 / aspect` — **55.42 m at 16:9**, 41.24 m at 2.389, 27.71 m at 32:9. That is a gameplay change (how far ahead you can see is how far ahead you can plan) and the owner chose it deliberately, twice, over having a second sprite in the frame.

The cap exists because the surplus width outside `Tuning.COLUMN_HALF_WIDTH` is **rock**, and the cliff art is one tile — so an uncapped wide panel showed it repeating (four reflections a side at 2.389). Capping the width is what makes "exactly one cliff sprite at each end" structural.

**The cap is `2 * RockFace.BODY_INNER_HALF_WIDTH`, and each half of that is load-bearing.** Not the quad's width: a wall tile's last `EDGE_INSET_METRES` hold no alpha (that margin is what puts the ragged silhouette on the column boundary), so capping there left 2.715 m only the body could fill. And not `CREST_OUTER_HALF_WIDTH` either: its outermost texel is the transparent wrap border, so capping there made the extreme pixel column empty at every aspect. One texel in is the last opaque column of the art, and the body's span is then exactly zero. Measured: half-width pinned at 49.258 m, **0 body tiles**, frame edge opaque, at 16:9, 2.389 and 32:9.

It is `max`, not `min`. `min` is the engine `Camera` entity's contain fit, which `CameraRig` exists to avoid — it would show *less* than 60 m of depth on a panel *narrower* than the design aspect. `max` never takes depth away below the design aspect, only above it. `CameraInvariants` checks whichever regime applies, on the real framebuffer, once a second under `EPT_DEV`.

**Solid rectangles go through `render/Draw.kt`.** `fillRect(x, y, w, h)` for a top-left rect, `fillRectCentred(x, y, w, h, angle)` for anything whose position means a *middle* — every object in the world, and the HUD's bubbles and depth-tape markers. The centred form exists because the art is normal-mapped sprite sheets, and a normal-mapped sprite is the **same world rect submitted to two surfaces** (albedo on `main`, normal on `gi_normal_map`); `drawTexture`, `NormalMapRenderer.drawNormalMap` and `GiSceneRenderer.drawLight` all take the identical `(x, y, w, h, angle)` + centre-origin tuple, so that second draw must be a copied argument list and never a second derivation. `DiveRenderer.drawDiver` is the worked example — the second call's arguments there are literally copied from the first — and the rock faces, the pearl and the air vents each follow it. (It read "the one place that does it" long after the rock art landed.) Do **not** reach for the engine's `NormalMapped` interface: `NormalMapped.kt:32` hands the renderer the whole asset, which for a `SpriteSheet` stretches all 42 cells across the quad with no way to name a frame.

**`score/` — persistence.** `ScoreRepository` is registered as an engine `Service` so it gets `onCreate` (load) / `onDestroy` (final synchronous save) from the engine lifecycle. Writes go to a temp file then `promoteAtomically` (`AtomicFileSwap`), with periodic timestamped backups. `InitialsEntry` is the three-letter arcade entry; `Leaderboard` ranks and decides what's worth recording.

**The main menu (2026-08-31 — the booth-to-desktop retarget, §0 of `docs/superpowers/specs/2026-08-30-main-menu-and-graphics-options-design.md`).** `render/MenuModel.kt` is pure, engine-free navigation over a `MenuPage` (ROOT / GRAPHICS) and a fixed `MenuItemId` row list per page — edge-triggered exactly the way `score/InitialsEntry` already is, and for the same reason: the engine's `Gamepad` exposes only `isPressed`/`getAxis`, no `wasClicked`, so a level reading has to be re-edged by hand or a stuck contact on a noisy encoder would scroll the whole list in one frame. `render/MenuLayout.kt` is its presentation twin, modelled directly on `AttractLayout`/`PauseLayout`/`BriefingLayout` — fractions of screen height, vertical anchors are the top of a text box. `EnPustTil.drawMainMenu` is the drawing; it reads a `MenuModel` field and a `settings.GameSettings` field, both still at their resting/compiled-default state as of this writing (see the paragraph below — the input wiring that would move them is a separate, deferred task, tracked in that plan's Tasks 7-8).

**`settings/` — the player's graphics/window preferences, separate from `score/` and from `application.cfg`.** `GameSettings` is an 8-field data record (`quality: String`, window size, render scale, fullscreen, frame cap, vsync, show-fps) with a `clamped()` that degrades any out-of-range or unknown field to its default rather than letting a hand-edited or stale file break — the same contract `score/ScoreRepository` already has for `scoreboard.json`. `quality` is deliberately a `String`, not a `render.GraphicsQuality`, so a JSON parse failure on one bad enum name cannot take the rest of the file down with it; `GameSettings.KNOWN_QUALITIES` (`internal`, mirrored by hand from `GraphicsQuality.entries`) is what `clamped()` checks it against, and `render.GraphicsApplierTest` asserts the two stay in sync so a future fourth preset cannot silently become unselectable. Settings persist to `~/EnPustTil/settings.json`, beside `scoreboard.json` and its backups, via `SettingsStore`/`EngineSettingsStore` wrapping `engine.data.saveObject`/`loadObject` — never the atomic-swap machinery the scoreboard uses, because a lost graphics setting costs one re-selection, not a player's run. **A corrupt or missing settings file degrades to `GameSettings.DEFAULT` and a WARN log; it can never block a boot** — see `SettingsStore`'s class doc for the full argument.

**`render/GraphicsApplier.kt` is the ONLY file in this game permitted to write engine graphics state** — GI scales, the render surface's own texture scale, target fps, screen mode, vsync. Everything a menu selection changes funnels through its `apply(settings, gi)`. Its class doc carries four traps that each cost real debugging time to find and are invisible in a diff: `lightTexScale` is a step function (the light texture rounds UP to `2^cascadeCount`, so a smaller scale can round to a BIGGER texture — never assume area scaling, evaluate through `render/GiSizing.kt`); `traceWorldRays = false` does not remove the global scene chain (those surfaces are created unconditionally and only a shader branch is gated — `globalSceneTexScale` must drop too, or the "saving" is imaginary); `gi_light_final`/`gi_normal_map` are unreachable through any `GlobalIlluminationSystem` property, so a direct `setTextureScale` on either STICKS where a change to one of the seven GI-owned scales would not; and `mergeCascades` must never be exposed on any menu row — turning it off collapses lighting to the single finest interval. **VSync has no engine API.** `WindowImpl.createWindow` calls `GLFW.glfwSwapInterval(0)` — the only such call in the jar — and re-applies it on every window recreation, which `Window.updateScreenMode` triggers whenever the screen mode actually changes. So toggling fullscreen from the menu silently turns vsync back off unless something re-asserts it; `GraphicsApplier.reassertVsync` is that something, and `apply` calls it unconditionally after every `updateScreenMode`, not only when the vsync setting itself changed.

**`booth/` — surviving two unattended days.** Three files, each solving a way the cabinet could go dark with nobody watching. `BoothLog` exists because `LogTarget` has no FILE entry (verified: it is a two-value enum, STDOUT and CONSOLE) and the release binary is a windowed GUI executable with no attached console, so STDOUT reaches nobody — `BoothLog.install` tees `System.out`/`System.err` into a file beside the scoreboard instead. `CallbackGuard` exists because the engine's own handler on an uncaught throwable opens **Notepad**, full-screen, in front of a queue (`writeAndOpenCrashReport` → `FileUtilsKt.openFile` on a `.txt` crash report, disassembled from the jar) — catching per callback keeps the cabinet alive through a bad frame instead. `CallbackSites` is the five callback-name constants `CallbackGuard` is keyed by; it lives beside `CallbackGuard` rather than in `EnPustTil`'s companion object so that companion can stay `private`. See `src/main/kotlin/booth/README.md`. **This machinery is intact and deliberately so, even though the target moved to a desktop Mac with a controller (see the note at the top of this file).** `RunLifecycle.EXIT_HOLD_SECONDS`, `MENU_IDLE_TIMEOUT_SECONDS`, `PAUSE_IDLE_TIMEOUT_SECONDS` and the initials-entry auto-submit are all still in force and still tested — a future booth build changes the boot state and hides the menu's QUIT row, it does not rewrite the state machine underneath them.

**Presentation state must never leak into `dive/`.** `DiveSim` simulates one run and nothing else; attract mode, dwell timers and initials entry live in `RunLifecycle`.

### The pure-logic-extracted-for-testing pattern

Anything worth asserting is pulled out into an engine-free object so it can be tested without a GL context: `Framing`, `CameraRig`, `CameraInvariants`, `DepthBlend`, `AimAngle`, `RunLifecycle`, `ControlHints`, `AttractLayout` and `ScreenText` (both in `EnPustTil.kt`), `parseDailySeed`, `textOutlineOffset`, `DiveRenderer.zone*At` / `stripCount` / `stripCentreDepth`. When you add rendering or layout logic, extract the *relationship between the numbers* the same way rather than leaving it inline in a draw call. `DiveSim` exposes `internal fun debug*` hooks for the same reason.

### Frame ordering is load-bearing

Lights are drawn from `onRender`, in the same call that drives `DiveRenderer`. Keep them there: `GiSceneRenderer`'s batch has to be filled before `gfx.drawFrame`, and `onRender` is where the rest of the drawing lives.

**Light-versus-geometry alignment is now structural rather than procedural.** GI's local scene surface is created with `camera = engine.gfx.mainCamera` — the same object `mainSurface` uses — and every matrix is built once per frame in `gfx.initFrame` before any game code runs. A light at world `(x, depth)` and a square at world `(x, depth)` therefore go through the identical matrix and *cannot* drift, whichever callback issued them. You could not reproduce the old one-frame bug on purpose.

**The remaining drift risk is the HUD**, which is on its own screen-space camera and so has to transform the diver's position by hand. It must take that anchor from `mainCamera.worldPosToScreenPos` in `onRender` — the same matrix the world is being drawn with this frame — and never from `DiveCamera.depth`, which is camera state from a different point in the frame and would put the air ring one frame ahead of the diver.

**Camera easing runs on the FIXED TICK, not the render clock.** An earlier version of this file described render-clock easing as deliberate; that became actively wrong when `CameraRig` took over `engine.gfx.mainCamera`. `updateViewMatrix` interpolates every camera parameter from a snapshot taken at the top of each fixed step, so writing the camera from the render clock pairs values that were never consecutive fixed states and makes the interpolator judder. Nothing is lost: `DiveCamera`'s easing is `1 − e^(−k·dt)` and already frame-rate independent, and the engine's interpolator then produces *smoother* motion above 60 fps than a render-clock write did. `CameraRig.snap` (not `apply`) is what `DiveCamera.snapTo` pairs with, because that snapshot starts at the identity and frame 1 is otherwise drawn with it — see `CameraRig`'s class doc for the measurement.

Inside `DiveSim.tick`, the order of surfacing / air burn / pickup / anglerfish is deliberate and each ordering constraint is commented where it lives. Don't reorder without reading those comments.

## Platform constraints — verified, not guessed

These were each established empirically (several by decompiling `pulse-engine-0.13.0.jar`) after a bug that produced no error message at all. Violating one fails silently.

- **`Surface.drawQuad()` and `drawLine()` render nothing on macOS/Apple Silicon** — no GL error, no log. The cause is *not* the shader `#version`, which an earlier version of this file claimed: `QuadRenderer.kt:37` and `LineRenderer.kt:34` declare the colour vertex attribute as `GL_FLOAT` (so it binds through `glVertexAttribPointer`) while `quad.vert`/`line.vert` declare it `in uint`. Feeding an integer vertex input through the float path is undefined behaviour; the shader derives alpha as `(rgba & 255u)/255.0`, so the undefined value yields **alpha 0** and the geometry rasterises fully transparent. `TextureRenderer`/`TextRenderer` bind the same attribute as `GL_UNSIGNED_INT` and work. Believed macOS-only — Windows drivers pass the 32 bits through — so it reaches no players. We shadow the two shaders from `src/main/resources/pulseengine/shaders/renderers/` for local development and the scene editor, and the release jar **deliberately keeps the engine's broken copies** (see `build.gradle.kts`). So game code must still use `Surface.fillRect()` / `fillRectCentred()` from `render/Draw.kt`: folding either into `drawQuad` would look correct on a Mac and fail silently at the booth. `DrawTest.no production source draws a quad or a line` fails the build if a call to `drawQuad`/`drawLine` (or their `*Vertex` forms) ever returns, and `fillRectCentred` offers the rotation that is the usual reason to reach for `drawQuad` in the first place. Full investigation in `docs/superpowers/reports/2026-08-06-drawquad-macos-investigation.md`.
- **`engine.window.width/height` are PHYSICAL framebuffer pixels**, not the logical size in `application.cfg` (2400×1800 on a Retina Mac from a declared 1200×900). Express sizes as a fraction of screen **height**, never width and never a pixel count — the booth display's aspect ratio is not known in advance. **The world no longer consumes this at all**: sizes there are metres (`render/Framing.kt`), and only `CameraRig` turns a metre into a pixel. Screen-space code — the HUD, the attract screens — should prefer `surface.config.width/height` over `engine.window.*`: they are the same number today, but `config` is what that surface's own projection was built from, so it is the only value that cannot disagree with what is actually being rendered. Reading the window instead is one half of the mechanism that shipped in `6ea1f53`'s bug.
- **The default font can only draw U+0020..U+011F.** Anything above that renders as *nothing at all* — no glyph and no x-advance, silently. Em dashes, en dashes, curly quotes, ellipses and bullets all vanish; Norwegian æøå are fine. Every drawn string goes through `ScreenText`, and `AttractScreenTest` asserts all of them are drawable, so a smart-quote substitution fails the build instead of reaching the booth. Use `ScreenText.SEPARATOR` (a middle dot) where you want an em dash.
- **A generic arcade USB encoder may have no SDL gamepad mapping**, in which case it is completely invisible to `engine.input.gamepads` while working fine at the OS level. `logGamepadDiagnostics` goes to the raw GLFW joystick API to tell "nothing plugged in" apart from "plugged in but unmapped", and logs the latter at WARN so it survives the booth's default log level.
- **An arcade encoder's joystick may enumerate as a HAT rather than as analog axes**, so reading only `GamepadAxis.LEFT_X`/`LEFT_Y` leaves a cabinet **startable and unplayable**: `restartButton` is a button and buttons work, so the run starts normally and the diver never moves, with nothing at all in the log. That is the same failure `selectGameplayPad` guards against, arriving through a different door. Every steering read — `readInput` and `readInitialsCycle` — therefore goes through `render/PadAxis.kt`, which resolves analog → D-pad → keyboard as *first live source wins* (a live stick passes through at full magnitude, because quantising it would turn every pad into a D-pad) and cancels both-directions-at-once to zero, so a stuck contact cannot pin the diver sideways for the rest of the day. Add a new steering source there, not inline.
- **`Gamepad.id` IS the raw GLFW joystick index.** `InputImpl` filters `glfwJoystickPresent(i) && glfwJoystickIsGamepad(i)` and constructs `Gamepad(i)` — verified from the 0.13.0 bytecode — which is what makes `glfwGetGamepadName(pad.id)` legitimate rather than a coincidence that happens to work on a machine with one pad. `render/ControllerFamily.kt` uses it to print the pad's own legend (`CROSS` on a DualSense, `A` on a generic encoder); the name read allocates a `String`, so it is gated on the deciding pad's id changing and never called per frame.
- **`Gamepad.isPressed`/`getAxis` READ THE DEVICE RAW AND INDEX IT BY SDL CODES, so every name in `GamepadButton` is fiction on a real pad. `render/MappedPads.kt` is now the only correct way to read a pad in this project — never `pad.isPressed`.** From the 0.13.0 bytecode: `Gamepad.updateState()` is exactly two calls, `GLFW.glfwGetJoystickAxes(id)` and `GLFW.glfwGetJoystickButtons(id)` — the RAW joystick APIs, i.e. the device's own HID report order — stored to two fields; `isPressed` then does `buttons.get(button.getCode()) > 0` and `getAxis` does `axes.get(axis.getCode())`, indexing that raw buffer by the **SDL-standard** code the enum carries. Meanwhile `InputImpl` only constructs a `Gamepad` for a joystick passing `glfwJoystickPresent(i) && glfwJoystickIsGamepad(i)`, and `Gamepad.id` IS that raw joystick index — so the engine filters to SDL-*mapped* devices and then reads them *unmapped*. Measured on the owner's DualSense (gamepad-mapped, `glfwGetJoystickName(0) == "DualSense Wireless Controller"`): `kickButton = A` (code 0) hit **Square**, `bleedButton = B` (code 1) hit **Cross**, and `restartButton = START` (code 7) hit **R2** — so **the Options button, the one the attract screen tells a queue to press, did nothing at all**. The left stick worked only by luck (axes 0/1 are LX/LY in both orders); the EPT_DEV overlay reading `RIGHT_Y=-1.00 LEFT_TRIGGER=-1.00` on an untouched pad was the same defect in the axes. The fix is `GLFW.glfwGetGamepadState(jid, state)`, which returns the SDL-mapped 15 buttons / 6 axes in exactly the order the codes assume — safe precisely because every pad in `engine.input.gamepads` has already passed `glfwJoystickIsGamepad`, which is that call's own precondition. `MappedPads` samples it once per frame (`updateGame`'s first statement, after the engine's `pollEvents` and before every `onFixedUpdate` and `onRender` of that frame) into primitive arrays keyed by joystick id, and a pad the mapped read ever refuses falls back to the raw read rather than going dead — a cabinet with an odd button map beats a cabinet that stops responding. **No config or label change was needed**: `ControlHints`/`ControllerFamily` were already printing `CROSS kick` for `kickButton = A`, and that only became true with this file. `MappedPadsTest.no production source reads a gamepad outside MappedPads` fails the build if `.isPressed(`/`.getAxis(` ever reappears on any receiver but `mappedPads` or `engine.input` (the keyboard).
- **The engine's `Gamepad` exposes only `isPressed`/`getAxis`** — there is no `wasClicked` for a controller button. Everything consuming lifecycle input takes level readings and does its own previous-frame edge detection (`RunLifecycle`, `InitialsEntry`). A stuck button on a booth encoder must never be able to restart the game repeatedly or blast through the alphabet.
- **Gameplay input reads gamepad 0; lifecycle input scans every connected gamepad** (`anyLifecycleActionPressed`). Index 0 is not guaranteed to be the cabinet's stick, and "any button to start" has to mean any.
- **The HUD lives on its own surface**, not `mainSurface`. `GlobalIlluminationSystem` multiplies `mainSurface` by the light map — which is what makes the Abyss dark, and would also multiply the HUD into near-invisibility. Its `zOrder` is pinned explicitly (`HUD_Z_ORDER`), because the engine otherwise assigns one by surface creation order.
- **The GI composite onto `mainSurface` is a MULTIPLY. This is settled — do not reopen it.** Two agents reached opposite conclusions from the same jar, so here is the decisive citation. `GlobalIlluminationSystem.onUpdate` — *not* `onCreate`, which is why disassembling only the surface-setup path misses it entirely — builds `MultiplyEffect("gi_blend_effect", 15, "gi_light_final", minReflectance)` (constructor descriptor `(Ljava/lang/String;ILjava/lang/String;F)V`) and hands it to `Surface.addPostProcessingEffect` on `gfx.getSurface(targetSurface)`, where `targetSurface` is initialised to the literal string `"main"` in the system's own constructor. `MultiplyEffect.applyEffect` then binds `tex0` from `textures.get(0)` — the effect's own input, i.e. `mainSurface`'s render texture — and `tex1` from `getSurface("gi_light_final")`, and `shaders/effects/texture_multiply_blend.frag` is `fragColor = vec4(c0.rgb * c1.rgb, c0.a)` guarded by `if (length(c0.rgb) < minReflectance) c0.rgb = vec3(minReflectance);`. So the reflectance floor bites on **c0, our albedo** — which is what `DiveRenderer.GI_REFLECTANCE_FLOOR` and `floorBlueForReflectance` exist for, and why an outline drawn as albedo cannot survive the deep (the reverted rim light, `d6faaa5`).
- **`pulseengine/shaders/lighting/global/final.frag:59` really does end `fragColor = vec4(base + light, 1.0)` — and that is NOT the composite.** It is the light map assembling itself. `GiFinal` is added as a post-processing effect on the **`gi_light_final` surface**, created a few instructions earlier in the same method, so its `baseTex` (bound from `textures.get(0)`) is that surface's own texture and never `mainSurface`; the `gi_local_scene` name `GiFinal` is constructed with goes to a *different* uniform, `localSceneTex`. `gi_light_final` is named by no other class in the whole jar, and nothing draws into it — it exists solely to host `GiFinal` and be sampled as `tex1` by the multiply above. Both readings were true statements about different stages; only one of them is the composite.
- **`SpriteSheet`'s constructor takes `(…, format, maxMipLevels, hCells, vCells)`** — the argument order is *not* the field declaration order, which reads `horizontalCells, verticalCells` first. Passing `(…, cols, rows, 0)` sets `hCells = rows` and `vCells = 0`; the constructor accepts that combination without complaint and silently builds a zero-length `Texture[]` — the misconfiguration itself raises nothing. It only surfaces two stages later, as a thrown `ArrayIndexOutOfBoundsException` from `getTexture(0)` the first time a frame is drawn, by which point the call site that actually got it wrong is off the stack. Verified from bytecode: the 6th int is forwarded to `Texture.<init>`'s trailing `maxMipLevels`, and the synthetic defaults constructor defaults that slot to `5`, pairing with the `LINEAR_MIPMAP` filter default.
- **`maxMipLevels = 0` allocates no texture storage at all.** `TextureArray` computes `mipLevels = min(maxMipLevels, floor(log2(size)) + 1)` with no `coerceAtLeast(1)` and hands it to `glTexStorage3D` as `levels`; `levels = 0` is `GL_INVALID_VALUE`, so nothing is allocated and every later `glTexSubImage3D` fails too — no exception, no log. `1` is the value that means "one level, no mips". `tools/build_spritesheet.py` prints the correct constructor call for exactly this reason.

## Performance shape — measured 2026-08-30, read before touching rendering

**The game is GPU-bound and the GPU is saturated.** At 100% device utilisation
(`ioreg -r -d 1 -c AGXAccelerator`; an idle desktop reads 3-5%) even with the frame limiter
removed. The game's own Kotlin — sim, camera, HUD, light submission — is **0.3 ms of the frame**,
under 0.5%. Optimising Kotlin here buys nothing; removing GPU passes is the only lever.

**Frame time fits roughly `13 ms + 10.5 ms per megapixel`.** The fixed term is REAL GPU WORK, not
driver overhead: the jump-flood chains and the cascade levels are fixed-size passes that do not
shrink when the window does. That is why pass COUNT matters as much as resolution.

**Pass count matters more on this Mac than it would on the Windows booth machine.** Apple GPUs are
tile-based deferred renderers: every render pass costs a tile-memory load at the start and a store
at the end, so ~85 passes with large RGBA16F attachments means gigabytes per frame of tile traffic.
A discrete desktop GPU with dedicated VRAM shrugs at many-small-passes; a TBDR is punished by it.
GL 4.1 on macOS also has no compute shaders, so the whole GI solve runs as fragment passes over
full-screen quads — a structural penalty of the deprecated API, not a slow chip.

**FULLSCREEN IS THE CHEAP PATH, AND THE COMPARISON IS NOT WHAT IT LOOKS LIKE.** `screenMode =
FULLSCREEN` obtains a REAL 1920x1200 exclusive video mode (verified: a `screencapture` of the
fullscreen game came back as a 1920x1200 PNG with no macOS chrome). A windowed "1920x1200" is
**logical points**, and under Retina scaling renders a substantially larger physical framebuffer.
Measured gap: **~2.8x**, mostly resolution rather than compositor bypass. So **every windowed
measurement overstates the real cost**, and a dev-window observation is a pessimistic one.

**Measured state after the 2026-08-30 performance work** (`docs/superpowers/specs/2026-08-30-rendering-performance-design.md` §6):
`targetFps` was 120 and **never once reached**; it is now 60 and **held solidly**, p95 sitting on
the cap. Windowed 1920x1200 holds 60 fps in both the attract screen and at 140 m; fullscreen
attract runs at ~226 fps uncapped. Fullscreen at 140 m was never measured.

**Measuring it yourself:** `EPT_PROFILE=1` runs `render/FrameProbe.kt`, which prints
`[FRAME] p50=... p95=... worst=...` once a second to stdout. Three traps:
- **`./gradlew run` silently reverts a resolution edit.** It re-triggers `processResources`, which
  restores `build/resources/main/application-dev.cfg` from source before the JVM launches. Use
  `./gradlew run -x processResources`, and edit only the gitignored build output, never `src/`.
- **Never measure under `EPT_DEV=1`** — the MetricViewer overlay is permanently visible in dev mode
  and adds an always-on draw every frame.
- **GL timer queries are dead on Apple Silicon.** `gpuProfiling = true` yields a well-formed
  85-scope tree with `t=0ns` on every node, because `GpuTimeQuery` uses `GL33.glQueryCounter`, which
  Apple's shim does not implement. The pass NAMES are still useful; the times do not exist. And
  `data.gpuRenderTimeMs` is **CPU wall time** around `drawFrame` + `swapBuffers`, despite the name.

**Two more engine facts worth knowing before adding code:**
- **Game callbacks run on a separate `"game"` thread, not the GL/main thread.** `gameLoopMode`
  defaults to `MULTITHREADED` and nothing here overrides it; `gfx.drawFrame` and `swapBuffers` run
  on the main thread. A direct GLFW/GL call from `onUpdate`/`onRender` is therefore on the wrong
  thread. `WindowImpl.initFrame` is the main-thread hook.
- **Every boot logs 31 ERROR lines and all are benign** — two for
  `pulseengine/shaders/error/error.comp` (a compute shader GL 4.1 on macOS does not have) and 29
  `Config property ... not found` for the deliberately commented-out `dailySeed`, button-map and
  `stickDeadzone` keys, whose fallbacks fire correctly on the next line. Worth stating precisely
  because 31 ERRORs on a clean boot is exactly the noise that hides a real fault.

## Config and release

`application.cfg` is the **booth default** and ships in the release `.exe`: fullscreen, no pinned window size (takes the display's native resolution), `logLevel = WARN`. `application-dev.cfg` is loaded automatically on top of it by the engine and restores windowed + DEBUG for local `./gradlew run`; it is excluded from the release by the `exclude("*-dev*")` line in `build.gradle.kts`. **`screenMode` CAN be changed at runtime, and window size can be too — this file said otherwise for months and was wrong.** `Window.updateScreenMode(ScreenMode)` is a public method on the `Window` *interface*: `WindowImpl.updateScreenMode` early-returns on no change, else queues a lambda through `runOnInitFrame` which calls `createWindow()` passing the PREVIOUS handle as GLFW's **share** parameter — so the new window inherits the old GL context's objects — then fires `resizeCallBack(w, h, windowRecreated = true)`, reaching `gfx.onWindowChanged`, which re-inits every surface and re-projects every camera. `init.pes` names this exact mechanism one paragraph before denying it exists. For window SIZE the old claim is *literally* true but misleading: there is genuinely no `glfwSetWindowSize` anywhere in the jar, but the window is created `GLFW_RESIZABLE`, the framebuffer-size callback is wired, and `SurfaceImpl.init` reallocates every render texture on resize — **dragging the window edge already works end to end today**, `CameraRig` included, and programmatic control is a ~10-line `WindowImpl` subclass (verified `open`, with an `open initFrame`). What IS startup-only is the INITIAL size and mode: `ConfigurationImpl.setWindowWidth/Height` have no effect after `WindowImpl.init` caches them, which is why this dev/booth config split still exists.

**Day two at the booth:** uncomment and change `dailySeed` in `application.cfg` and restart. That regenerates the water column and, because every `ScoreEntry` stores the seed it was earned under, gives day two a fresh leaderboard while day one's board stays intact in `scoreboard.json`. **The value must be a whole number, `2147483647` (`Int.MAX_VALUE`) or below.** `ConfigurationImpl.loadConfigFile` type-coerces every property value before storing it (all-digits → `Integer`, digits-with-one-dot → `Float`, anything else → `String`) — this is not a formatting nicety, it is why the procedure above did not actually work until `EnPustTil.resolveDailySeed` existed: every real seed used here (`20260902`, `20260903`) is all-digits and was being stored as an `Integer`, while the code read it with `engine.config.getString`, which returns null for anything not literally stored as a `String` — so day two silently reused day one's seed and appended to day one's leaderboard, exactly the failure `parseDailySeed`'s fallback contract claims to guard against, arriving through a different door. `resolveDailySeed` now checks `getInt` first, which fixes the common case. Going ABOVE `2147483647` is a SEPARATE and much worse failure that nothing at the call site can fix, and is worth stating precisely rather than approximately — "ten digits or fewer" is ACTIONABLY WRONG (`2147483648` is ten digits and fails; `2147483647` is also ten digits and is fine), and was corrected here after being printed once already. `Integer.parseInt` throws while `application.cfg` is being parsed. That throw is SILENT — the engine calls `ConfigurationInternal.init()` for this file, which is `runCatching { loadConfigFile(...) }` with the `Result` stored to a local that is never read (verified from bytecode: nothing after the `astore`); the OTHER method that logs `"Failed to load configuration"` at ERROR, `ConfigurationImpl.load(path)`, is never the one the engine calls for `application.cfg`. And it is NOT the whole file that reverts to defaults — an earlier version of this paragraph claimed that and it was also wrong: `loadConfigFile` iterates `Properties.entrySet()`, a `Hashtable`, so which keys survive is HASH ORDER, not file order, and every entry already reached before the throw is already committed. Measured against the real shipping file with `dailySeed = 99999999999`: most of the file survives — the cabinet does not come up windowed, `screenMode`/`logLevel` are intact — but the loss set is HASH ORDER dependent and is emphatically NOT "just dailySeed": that exact measurement also lost `restartButtonAlt`, one of the four button-map keys, so "the whole button map survives" is not a safe thing to say either (an earlier version of this very paragraph said it, and was wrong — the two passages had disagreed with each other, which is worse than either being wrong alone). The authoritative measured example — the full survive/lose key list specifically, as opposed to the boundary and mechanism explained above, which ARE deliberately repeated here because a technician standing at the booth needs them in this paragraph — lives in `EnPustTil.resolveDailySeed`'s KDoc: read that KDoc if this paragraph and it ever look different again, rather than trusting whichever one you found first. Which keys are lost for any GIVEN bad value is unpredictable and changes if the key set changes, so no fixed list belongs in either place. `EnPustTil.configFileHealthWarning` is a cheap runtime check in the same spirit (compares `gameName` read back against the compiled constant, since it can never itself be the value that throws) but its detection is SPECULATIVE, not reliable: it did NOT fire for either scenario actually measured here — `dailySeed` and `targetFps` above the ceiling both left `gameName` intact — so its silence means only "gameName survived," never "the file loaded completely," and must not be read as the latter. It also has a false-positive path nobody had documented until now: editing or removing the `gameName` line itself fires it with nothing truncated at all — application.cfg now carries a one-line note beside that key saying not to touch it. Verified empirically against the real `ConfigurationImpl`, including the exact boundary (`2147483647` loads, `2147483648` throws), not reasoned from the decompiled loader alone — see `.superpowers/sdd/2026-08-21-booth-survival/task-6-7-report.md` for the harness and full output, and read the full report rather than only its first pass — this exact paragraph has been revised more than once as later measurements corrected earlier ones.

**The macOS build is a `.app`, not the `.exe` — they are different artefacts and only one of them is the booth.** `buildWin64Release` cannot produce something a Mac can run, for two independent reasons: the launch4j output is a Windows PE launcher next to a bundled Windows JRE, and `tasks.jar`'s `exclude("macos/**", "linux/**")` (`build.gradle.kts:81`) removes the macOS natives outright — LWJGL's dylibs really do sit at top level in `pulse-engine-0.13.0.jar` (`macos/arm64/org/lwjgl/...`), so that line bites, and the release fat jar measures **0 `.dylib` against 12 `.dll`**. The Mac path is separate and additive; it changes nothing about the Windows one:

```bash
./gradlew buildMacRelease      # release/macos/One More Breath.app  (227 MB, self-contained)
./gradlew buildMacInstaller    # release/macos/One More Breath-1.0.dmg  (119 MB, .app + Applications symlink)
```

**`jpackage` MUST come from the Gradle toolchain, and this is the trap that eats a day.** `jpackage --type app-image` bundles the runtime of *the JDK it belongs to*, not the one the code was compiled against. This project compiles at `jvmToolchain(23)` while the system JDK here is **19**, so `/usr/bin/jpackage` builds a bundle pairing Java 23 class files with a Java 19 runtime. Nothing warns. It fails only at launch, inside a packaged `.app` whose stdout goes nowhere a double-click can see, so the symptom is "the icon bounces once and nothing happens" and the real error — `UnsupportedClassVersionError: EnPustTilKt has been compiled by a more recent version of the Java Runtime (class file version 67.0), this version of the Java Runtime only recognizes class file versions up to 63.0` — is never seen. The task therefore resolves `jpackage` through the `javaToolchains` service (`launcherFor { JavaLanguageVersion.of(23) }` → `metadata.installationPath`) and never from `PATH` or `JAVA_HOME`. Verified on the built bundle: `Contents/runtime/Contents/Home/release` reads `JAVA_VERSION="23.0.2"`. It also passes `--java-options -XstartOnFirstThread`, which is not optional — GLFW must own the process's first thread, and the `application {}` block only covers `./gradlew run`.

**What actually makes the bundle runnable is `installDist`, not the fat jar.** jpackage is pointed at `build/install/en-pust-til/lib`, which holds the ORIGINAL dependency jars beside the stripped fat one, and all four land on `app.classpath` — so the unstripped `pulse-engine-0.13.0.jar` supplies the dylibs that line 81 removed. Package the fat jar alone and the `.app` dies in GLFW init.

**The bundle is the BOOTH build: fullscreen, `logLevel = WARN`.** `tasks.jar` excludes `*-dev*`, so `application-dev.cfg` is not in it and the windowed/DEBUG override never applies. Measured on a launched bundle: after `Initializing configuration` the log carries **0 INFO and 0 DEBUG lines** (6 WARN, 31 ERROR — the ERRORs are absent-but-optional config keys, and `Daily seed: 20260902` prints at WARN), and the window comes up **1920×1200 at (0,0) on window layer 25**. There is no quit key. **From a RUN the way out is now Esc/Options, then the menu's QUIT row** — mid-run pause opens the main menu (see the PAUSED paragraph in `render/` above), and that menu has QUIT on it. The **hold-to-exit** route (`Options`, then hold **L1 + R1**; or `ESC`, then hold `Q` — `ControlHints.exitHold`, `RunLifecycle.EXIT_HOLD_SECONDS`) still exists and still works, but only from the **attract screen's** cabinet menu, which is the one half of PAUSED that still draws `drawPauseScreen` and its progress bar. This line said "the pause screen" without qualification until 2026-08-31, when mid-run pause stopped being that screen.

**The bundled process is named `One More Breath`, so every `EnPustTilKt` line in the capture procedures above misses it.** `pgrep -f EnPustTilKt` and `pkill -9 -f EnPustTilKt` match the Gradle `run` JVM and **not** the packaged app; use `pgrep -f "One More Breath"` / `pkill -f "One More Breath"`. The window-grab `osascript` line misses it for the same reason — the bundle's windows are owned by `One More Breath`, while `./gradlew run`'s are owned by `java`, so `first application process whose name is "java"` focuses the wrong one when both are up. That is not hypothetical: a window measured during this work turned out to belong to a concurrent `./gradlew run` (1600×928 windowed, i.e. `application-dev.cfg`) and was briefly mistaken for the bundle's. Filter `CGWindowListCopyWindowInfo` by `kCGWindowOwnerPID` against the pid you launched, and use `kCGWindowListOptionAll` — a fullscreen window that is not frontmost does not appear under `kCGWindowListOptionOnScreenOnly`.

**A `.dmg` does NOT make it run on someone else's Mac.** Gatekeeper blocks unsigned apps, and on Apple Silicon a quarantined unsigned app commonly reports **"damaged and can't be opened"** — which reads as a corrupt download and sends people to re-download rather than to the security settings. Real distribution needs a Developer ID certificate plus notarization, i.e. a paid Apple Developer account. Signing is wired but inert: pass `-PmacSigningIdentity="Developer ID Application: Name (TEAMID)"` and the tasks add `--mac-sign --mac-signing-key-user-name`; with the property absent those flags are omitted entirely, so a clean clone with no Apple account still builds a working bundle. Without a certificate the recipient must right-click → Open, or run `xattr -dr com.apple.quarantine "One More Breath.app"`. And the bundled runtime is **aarch64 only** (the launcher and `libjvm.dylib` are both Mach-O arm64) — it will not run on an Intel Mac.

**Sprite art.** `assets/` (183 MB; the diver's 1000×2000 frames, oxygen's 2000×2000) and `release/` are gitignored; the *baked* sheets in `src/main/resources/sprites/` are committed and ship in the `.exe`. A clean clone can build and run but cannot re-bake without the source frames. The bake is byte-reproducible, so re-running it with unchanged inputs produces no diff — which is the regression test for changes to the bake itself: re-bake `diver` and the committed PNGs must not move a byte. `docs/superpowers/specs/2026-08-07-diver-spritesheet-bake-design.md` is their specification; `DiverSprite` copies its grid numbers, and `DiverSpriteTest` re-derives them from the committed PNG's IHDR so a re-bake at a different `--frame-height` cannot leave them stale.

**A sprite set is data, not code** (`tools/spritesheet/sets.py`): a `SpriteSet` is an ordered list of `Layer`s over one shared frame index, and `Layer.kind` selects the resampling pipeline, the `TextureFormat` the printed Kotlin claims, and which validation gates run. Two things that looked structural in the diver are per-set: **a set need not have both layers** (oxygen is normals-only, so the pairing and alpha-agreement gates are skipped rather than failed), and **a duplicate tail frame is not universal** (the diver's frame 42 re-exports frame 1; oxygen's frame 96 does not, so `dropped_tail_frames` is 0 there). Adding a set is adding an entry to `SPRITE_SETS`.

**Frame height is a VRAM decision, not a sharpness one, and smaller is NOT always cheaper.** `TextureBank` allocates one **square** array per (bucket, format, filter, wrapping, `maxMipLevels`) with every layer eager, and reuses it only when all of those match **and `max(w,h) > arraySize/2`** — that last condition is easy to miss and is what makes the rule non-monotonic. Everything shipped today lands in the 2048 bucket, so 2048/SRGBA8 (240 MiB) and 2048/RGBA8 (240 MiB) are already paid for and a new sheet landing there is **free**. From `DEFAULT_CAPACITIES` in the 0.13.0 bytecode, anything else is not: 1024 costs +200 MiB, 4096 +640 MiB, 8192 +1280 MiB, each to hold one texture. Oxygen at 216 px (2002×1944) shares the existing array; at 224 px the grid search tips to a 6×16 layout 3584 px tall and buys a whole 4096 array; at 96 px it would be 984×768, fail the half-size test and allocate its own 1024 array. Re-run the grid search when changing `--frame-height` rather than assuming.

**`diver-normal.png` and `oxygen-normal.png` have a HYPHEN and must keep it.** The engine's `loadAll` auto-loader (`Extensions.kt:446-448`) keys on the substring `_normal` — an underscore — and, when it matches, forces `RGBA8` with **10** mip levels regardless of what the caller asked for. Renaming either to `*_normal.png` would silently give the sheet a mip chain, and mip generation averages across cell boundaries: adjacent frames of the loop would bleed into each other under minification. `test_registered_sets_declare_the_formats_their_kinds_require` fails the bake's own suite if a set is ever declared with an underscore.

## Conventions

- Allman braces, 4 spaces, no wildcard imports — match the surrounding file.
- Comments here explain *why*, often at length, and frequently cite the evidence (a decompiled engine class, a screenshot, a playtest). That density is deliberate: most of these decisions look arbitrary or wrong without it. When you fix something subtle, leave the same kind of note.
- No per-frame allocation in the render path. HUD text formatting is the one explicit exemption; `DepthBlend` and the colour ramps take and return primitive floats specifically to stay allocation-free.
- Simulation is deterministic: seeded RNG, fixed timestep, no `Math.random()` in `dive/`.
- Tests use `kotlin.test` on JUnit Platform, with backticked descriptive names. A test that cannot fail is worse than no test (commit 4493eeb deleted several) — assert the relationship that would actually break.
